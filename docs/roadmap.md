# 项目路线图：NexArm 主从遥操作链路与延迟测量

这份文档是做项目时的步骤参考。每个阶段都写了要做什么、怎么算做完、留下什么产出。
做完一个阶段就在末尾的进度表里打勾，并把实测结论补到对应小节。

## 1. 目标

在 NexArm 主从臂上自己搭一条"电脑在环"的遥操作链路，把端到端延迟拆开测量，
再做补偿，最后给出补偿前后的平均延迟和 P95，并写清测试条件。

三个要回答的问题：

1. 这条链路一轮读写要多久，实际能跑到多高的控制频率？
2. 端到端延迟是多少，分别花在采集、处理、下发、执行哪一段？
3. 滤波和前馈预测能把延迟降多少，代价是什么？

## 2. 已知事实（来自商家固件和 LeRobot 改版的源码）

这些是读代码得到的，还没有在真机上验证。阶段 1 的任务之一就是逐条确认。

| 事实 | 依据 |
|---|---|
| 主臂和从臂的 USB 口接的是 ESP32（CH340 串口，1 Mbps），不是舵机总线本身 | 商家 `README_NEXARM.md`、固件源码 |
| 从臂是 ESP32 + AT32F421 协处理器，舵机指令经 AT32 转发 | 从臂固件 `bridge_usb_callback` |
| 电脑和臂之间用自定义帧：`FF FF ID LEN CMD ARGS CHECKSUM` | `CommProtocol.h` |
| LeRobot 桥接模式：68 进入/退出，96 读 6 个位置，97 写 6 个位置，98 力矩开关 | `README_NEXARM.md` |
| 另有不进桥接模式的 69 号指令，可直接写 6 个目标位置加速度参数 | 从臂固件 `CMD_PC_SYNC_TEACH` |
| 舵机位置 12 位（0–4095）；2 号关节主从镜像（4096 − pos）；6 号夹爪映射到 [1195, 2833] | `mapMasterTeachToFollower` |
| 舵机寄存器地址（41 加速度、42 目标位置、56 当前位置、同步写 131）与飞特 STS 系列一致 | `HX_30HM_Def.h` |
| 出厂无线同步：主臂每 4 ms 逐个读 6 个舵机并用 ESP-NOW 广播，从臂收到即下发，全程无滤波 | 主臂固件 `send_teach_positions` |
| 商家 LeRobot 改版（0.5.2）自带 `nexarm_follower` / `nexarm_leader`，示例配置为 30 fps | `finsh.zip` |

**由此得到的一个预判：** 官方 LeRobot 的 so101 驱动直接讲飞特舵机协议，而 NexArm 的 USB 口后面是 ESP32
和自定义帧，所以官方 so101 类型很可能不能直接用，需要走商家改版里的 `nexarm_*` 类型。
这是预判，不是结论，以真机验证为准。

## 3. 总体思路

- **电脑在环。** 主臂、从臂都用 USB 接电脑：读主臂 → 处理 → 写从臂。不改固件，所有时间戳来自同一个时钟。
- **核心模块与硬件无关。** 滤波、预测、延迟统计只吃"时间戳 + 关节角"，不知道底下是什么臂。
- **驱动层自己写薄的一层。** 测量需要在每次串口收发前后打时间戳，自己写更可控；
  另外再做一个 LeRobot 适配层，让后续采数据能沿用这条链路。
- **激励要可复现。** 人手拖主臂每次都不一样，所以先录一段主臂轨迹，之后所有对比都回放同一段。
- **数字只属于这套系统。** 旧项目（Alicia-D → FR3）的延迟数据不搬过来，NexArm 上全部重测。

建议的仓库结构：

```
nexarm_teleop/
  driver.py        # 帧收发、读位置、写位置、力矩；每次收发带时间戳
  mapping.py       # 主从映射、限位、跳变检测、解绕
  filters.py       # OneEuro、固定低通
  predictor.py     # 线性外推前馈
  latency.py       # 互相关、阈值法、统计（均值、P50、P95）
  logger.py        # 每周期一行的记录
scripts/
  bench_io.py      # 阶段 2：读写耗时和频率
  step_response.py # 阶段 3：从臂阶跃/正弦响应
  record_leader.py # 录主臂轨迹
  teleop.py        # 实时遥操作（可切换各处理级）
  replay.py        # 回放轨迹做消融实验
  analyze.py       # 出图出表
tests/             # 不接硬件的单元测试（帧编解码、滤波、统计）
docs/              # 路线图、兼容性结论、技术报告
results/           # 小体积的汇总表和图；原始日志不进仓库
```

## 4. 分阶段步骤

时间是按每天投入两三个小时粗估的，仅供排期参考。

### 阶段 0：准备（约 1 天）

1. 建 Python 3.12 环境；把自己加进 `dialout` 组。
2. 两块板都是 CH340，设备名会随插拔顺序变。用 `/dev/serial/by-path/` 或 udev 规则固定成 `leader` 和 `follower`。
3. 记录固件版本（包里的出厂固件是从臂 V1.3、主臂 V1.1）。出厂 `.bin` 留好，刷坏可以恢复。
4. 安全：从臂周围清空；先确认急停方式（断电或力矩关闭指令）；任何新脚本先用小幅度、低速度试。

完成标准：两个串口名固定；能用一条命令关掉从臂力矩。

### 阶段 1：跑通与兼容性验证（约 2–3 天）

1. 用商家 LeRobot 改版按 `README_NEXARM.md` 跑通遥操作。这是基线，证明硬件没问题。
2. 用官方 LeRobot 的 so101 类型尝试找电机、校准、遥操作，记录每一步的现象和报错。
3. 对照第 2 节的表，逐条确认或推翻。
4. 写 `docs/compatibility.md`：能不能用、差异在哪一层（接口、协议还是寄存器）、要兼容需要什么。

完成标准：有一份带证据的兼容性结论；商家改版下从臂能跟随主臂。

### 阶段 2：自己的最小链路和时序基线（约 1 周）

1. 写 `driver.py`：帧编解码、进入桥接模式、读位置、写位置、力矩开关。先写单元测试再接硬件。
2. 写最简遥操作循环：读主臂 → 映射 → 写从臂，不加任何处理。
3. `bench_io.py` 测量并出表：
   - 单次读主臂、读从臂、写从臂的耗时分布（均值、P50、P95、最大值）。
   - 不带 sleep 时循环能跑到的最高频率。
   - 目标频率 30 / 50 / 100 / 200 Hz 下的实际频率、周期抖动、超时和丢帧率。
4. 定好日志格式，每周期一行，用 `time.perf_counter_ns()`：
   循环开始、主臂请求发出、主臂回复收到、主臂位置、处理后指令、写完成、从臂请求发出、从臂回复收到、从臂位置。

完成标准：一张读写耗时表；一个有依据的控制频率选择；裸链路能稳定遥操作。

### 阶段 3：端到端延迟拆解（约 1–2 周）

延迟的定义：**起点**是主臂关节实际动了，**终点**是从臂对应关节实际跟上。分四段：

| 段 | 含义 | 怎么测 |
|---|---|---|
| 采集 | 主臂舵机 → ESP32 → USB → 电脑 | 阶段 2 的读耗时；读到的位置有多"旧"需要外部真值校验 |
| 处理 | 滤波、预测、映射 | 日志里的时间戳相减；滤波的群延迟另算 |
| 下发 | 电脑 → USB → ESP32 → AT32 → 总线 | 写耗时；写完到舵机开始动的时间并入执行段 |
| 执行 | 舵机收到指令到实际位置跟上 | 阶跃和正弦响应 |

步骤：

1. **执行段单独测。** `step_response.py` 不用主臂，直接给从臂发阶跃和不同频率的正弦，读回位置。
   得到每个关节的起动延迟、上升时间、相位滞后。同时记录全局加速度参数的影响。
2. **录一段标准主臂轨迹**（包含快动、慢动、停顿、换向），存成文件。之后所有实验都回放它。
3. **端到端测量，两种算法都做：**
   - 互相关：主臂位置序列和从臂实测位置序列，找相关性最大的时间差，得到整体延迟。
   - 阈值法：沿用旧项目延迟探针的思路，每次明显动作产生一个延迟样本，得到分布，算均值和 P95。
4. **外部真值校验（建议做）。** 手机 240 fps 慢动作把主从臂拍进同一个画面，数帧得到延迟，
   和软件测量对比。因为软件读到的位置本身有延迟，这一步能发现系统性偏差。
5. 出图：延迟分解条形图、端到端延迟的分布图。

完成标准：裸链路的平均延迟和 P95；四段各占多少；一份测试条件清单
（固件版本、波特率、控制频率、加速度参数、负载、电源、轨迹、样本数）。

### 阶段 4：补偿（约 1–2 周）

1. 从旧项目移植并重调：OneEuro + 固定低通、跳变检测、角度解绕、线性外推预测。
   先确认 NexArm 舵机的位置是否会回绕，再决定解绕是否需要。
2. 回放同一段轨迹做消融，每种配置跑多次：
   - 无处理（基线）
   - 仅滤波
   - 滤波 + 预测，前瞻时长取若干档
   - 不同控制频率
   - 不同舵机加速度参数
3. 每种配置记录：平均延迟、P95、跟踪均方根误差、超调、高频抖动能量。
4. 画延迟和平滑度的权衡曲线，选一个推荐配置并说明理由。
5. 舵机 PID 也影响执行段，但改它有风险：先读出并记下出厂值，作为可选实验放在最后。

完成标准：一张补偿前后对比表（平均和 P95）；一张权衡曲线；推荐配置及其测试条件。

### 阶段 5：成果整理（约 3–5 天）

1. 重写 README：链路示意图、延迟分解图、补偿前后对比图和表、测试条件、复现命令、演示视频或动图。
2. 写 `docs/report.md`：方法、结果、局限、没做成的尝试。
3. 加一节"与上一套系统的对比"：同一套测量和补偿方法在 Alicia-D → FR3 和 NexArm 上各自的表现和差异原因。
4. 做 LeRobot 适配层，让滤波和预测能作为处理步骤插进采集流程。

完成标准：陌生人只看 README 就能明白做了什么、结果是什么、怎么复现。

## 5. 可选拓展

按"投入小、和主线衔接紧"排序：

1. **出厂无线直连 vs 电脑在环。** 出厂模式是两块 ESP32 用 ESP-NOW 直连、每 4 ms 一包。
   用外部真值（慢动作视频）测它的延迟，和电脑在环对比，说明电脑在环多付出了多少延迟、换来了什么。
2. **力反馈原型。** 前提是主臂能由电脑使能力矩（待验证）。用从臂的位置误差或负载寄存器估计受力，
   让主臂产生阻力。这是基于位置误差的原型，不是阻抗控制，写的时候口径要准确。
3. **绕过 ESP32 直连舵机总线。** 用半双工 USB 转接板直接上总线，验证寄存器是否真的与飞特 STS 兼容、
   官方 so101 驱动能否工作，并测出没有 ESP32 中转时的读写耗时。接线前确认信号电平。
4. **改固件降延迟。** 例如让 ESP32 主动高频推送位置而不是一问一答。收益可能大，但调试成本高，放最后。
5. **ROS 2 封装。** 把链路包成节点，发布关节状态和延迟统计。

## 6. 风险和判断点

| 情况 | 应对 |
|---|---|
| 官方 so101 不兼容 | 预期之内。走商家改版和自写驱动，把差异写进兼容性结论 |
| 一问一答的读写太慢，频率上不去 | 先量化瓶颈在哪一跳；考虑 69 号指令、减少读从臂的频率，或拓展 3、4 |
| 软件测得的延迟和视频真值差很多 | 以视频为准，分析差值来源（读到的位置有多旧），写进报告 |
| 预测带来超调或抖动 | 减小前瞻时长；在权衡曲线上如实呈现 |
| 人手激励不可复现 | 一律用录制轨迹回放做对比，人手只用于演示 |
| 舵机过热或堵转 | 实验间留冷却时间；读温度寄存器；限制幅度和时长 |

## 7. 实测记录

### 2026-11-13 串口探测（`scripts/probe_ports.py`，只读）

| 项 | 主臂 | 从臂 |
|---|---|---|
| 固定设备名 | `/dev/serial/by-path/pci-0000:00:14.0-usb-0:4.4.1:1.0-port0` | `/dev/serial/by-path/pci-0000:00:14.0-usb-0:4.4.2:1.0-port0` |
| 空闲时串口上有什么 | 每秒一行文本 `[POS] ... \| chassis=OFF` | 不停主动上报 11 号帧（6 个坐标 + 6 个舵机位置），夹杂 `[CB]`、`[FW]` 调试文本 |
| 96 号读位置（未进桥接模式） | 有回复，单次约 15 ms（仅一次采样） | 无回复，只打印一行 `[CB]` 日志 |
| 1 号查版本 | 无回复 | 回复，`ESP32=1.0.2` |

结论和注意点：

- 两块板的 CH340 没有序列号，只能按 USB 口区分，两条臂要固定插在现在的口上。
- 打开串口没有触发主臂重启（没有出现启动信息）。
- 从臂在普通模式下不响应 96 号指令，与"需要先用 68 号进入桥接模式"的源码结论一致。
- 两块板都会往串口里打调试文本，驱动解析时必须能跳过非帧数据。
- 从臂空闲时自己就在上报舵机位置，这是一个不用一问一答就能拿到从臂位置的途径，上报频率待测。

### 从臂的模式切换（真机观察）

- 开机后屏幕显示默认的机械臂状态界面。
- 按一次 KEY 1 进入 ESP-NOW 模式（接收主臂无线同步）；再按一次进入 WiFi 热点模式，屏幕显示热点信息。
- 从固件源码看，开机时内部状态就是"WiFi 热点运行中"，ESP-NOW 没有启动，只是屏幕没显示热点信息。
  第一次按键进的是 ESP-NOW 而不是热点，与此吻合。
- 所以跑电脑在环时，开机后不按 KEY 1 即可；只要屏幕不是 ESP-NOW 界面，无线同步就是关的。

### 2026-11-13 自写驱动首次真机检查（`scripts/check_bridge.py`，只读，各 100 次）

| 操作 | 均值 | 中位 | P95 | 最大 | 超时 |
|---|---|---|---|---|---|
| 读主臂 6 个位置（96 号） | 13.81 ms | 13.79 ms | 14.07 ms | 15.07 ms | 0 |
| 读从臂 6 个位置（桥接模式，96 号） | 4.58 ms | 4.56 ms | 4.78 ms | 4.84 ms | 0 |

测试条件：两臂静止；从臂在 WiFi 热点模式下进入桥接模式；1 Mbps；主机 Ubuntu，Python 3.12，pyserial 3.5；耗时为"请求写入串口前"到"回复帧解析完成"。

- 桥接模式在真机上可用：68 号进入后，96 号读位置正常回复。
- 读主臂比读从臂慢约三倍。主臂固件是逐个舵机读，每读一个固定等待 800 µs，6 个就是 4.8 ms 的纯等待；从臂由 AT32 协处理器读。
- 只按"读一次主臂"算，循环频率上限约 70 Hz；如果每周期还读一次从臂，约 54 Hz。写指令的耗时还没测。
- 两臂静止时，从臂实际位置与主臂映射后的目标相差 2–10 个计数（一圈 4096）。

### 2026-11-13 第一次裸链路遥操作（`scripts/teleop.py`，30 秒，人手拖动主臂）

链路时序（1444 个周期，超时 0，坏读数 0，被限幅 0）：

| 项 | 数值 |
|---|---|
| 实际控制频率 | 48.1 Hz（目标 50 Hz） |
| 周期 | 中位 20.09 ms，P95 22.57 ms，最大 24.51 ms |
| 读主臂 / 读从臂 | 中位约 13 ms / 约 6 ms |
| 电脑处理（主臂回复到发出指令） | 中位约 0.08 ms |

从臂滞后的初步估计（把指令序列在时间上平移，找与从臂实测位置最吻合的平移量；
时间戳取每次读取的请求和回复的中点；跳过前 2 秒过渡）：

| 关节 | 运动范围（计数） | 指令峰值速度（计数/秒） | 最吻合的滞后 |
|---|---|---|---|
| 1 | 410 | 912 | 76 ms |
| 2 | 545 | 1048 | 116 ms |
| 3 | 520 | 998 | 84 ms |
| 4 | 925 | 2178 | 78 ms |
| 5 | 324 | 926 | 104 ms |
| 6（夹爪） | 36 | — | 运动太小，未估计 |

测试条件：舵机加速度参数 100、速度上限 2000（商家改版默认值）；每周期步长限制 60；空载；人手激励，单次运行。

这只是初步数字，局限：

- 人手激励，不可复现，只跑了一次。
- 读到的位置在读取窗口（主臂约 13 ms、从臂约 6 ms）里的哪一刻采样并不知道，取中点是假设，会带来几毫秒量级的不确定。
- 这是"电脑看到主臂位置"到"电脑看到从臂跟上"的滞后，不含主臂采集本身的延迟，所以真实端到端延迟比它大。
- 加速度和速度参数直接影响执行段，换参数数字会变。

### 2026-11-13 从臂阶跃响应（`scripts/step_response.py`）

每格是来回共 10 次的中位数，时间从"指令写入串口前"算起。

|---|---|---|---|---|---|
| 100 / 2000 | 1 | 33.9 ms | 82.8 ms | 137.3 ms | 0.5 计数 |
| 100 / 2000 | 2 | 44.2 ms | 100.0 ms | 195.5 ms | 9.5 计数 |
| 100 / 2000 | 4 | 37.8 ms | 69.6 ms | 113.0 ms | 9.0 计数 |
| 0 / 2000 | 1 | 34.7 ms | 83.7 ms | 136.0 ms | 1.0 计数 |
| 0 / 2000 | 2 | 46.5 ms | 98.5 ms | 184.4 ms | 10.0 计数 |

### 2026-11-14 慢动作视频：外部真值（`scripts/video_latency.py`，`results/video_latency.csv`）

| 配置 | 来源 | 次数 | 走到 10% | 走到 50% | 走到 90% | 从臂超调 |
|---|---|---|---|---|---|---|

| 不开预测 | 串口日志 | 12 | 75.4 ms | 86.4 ±1.7 ms | 82.7 ms | 7.2% |
| 逐关节预测 | 视频 | 9 | 76.2 ms | 68.6 ±12.3 ms | 46.5 ms | 31.5% |

- **视频校验了时间基准**：用每次甩动的时刻把视频时钟对到日志时钟，斜率 1.00013 和 0.99864，残差 14–22 ms，说明视频时间戳是真实时间。
- **真实端到端延迟（走到 50%）：不开预测约 100 ms，开预测约 69 ms，降了约 31 ms。** 这是在真实主臂、现场遥操作下测的，不是回放。

- 视频里从臂的超调比编码器读数大（12% 对 7%），可能是连杆柔性或齿轮间隙，编码器看不到；也可能是跟踪误差。未验证。
- 局限：视频方差明显大于日志（±11–12 ms 对 ±2–4 ms），而且两个方向的甩动在视频里差约 18 ms，日志里只差约 2 ms，
  说明视频跟踪本身有方向相关的误差（透视、手入镜、区域选取）。均值可信，单次不可信。只测了底座一个关节。

### 2026-11-14 控制频率、输入滤波、逐关节前瞻搜索（`results/replay_summary_batch3.csv`）

第二段轨迹回放，关节 1–5 合并。控制频率的对比里，每周期步长按频率折算（25 / 50 / 100 Hz 对应 160 / 80 / 40 计数），保证速度上限相同。

| 配置 | 回放次数 | 滞后均值 | 滞后 P95 | 跟踪误差 RMS | 抖动 RMS |
|---|---|---|---|---|---|
| 50 Hz，无预测（今天重测） | 2 | 82.7 ms | 110.0 ms | 27.7 | 1.30 |
| 25 Hz，无预测 | 2 | 95.0 ms | 119.9 ms | 32.4 | 不可比 |
| 100 Hz，无预测 | 2 | 76.0 ms | 115.0 ms | 24.5 | 不可比 |

- **可重复性**：50 Hz 无预测今天 82.7 ms，昨天 84.2 ms。
- **控制频率**：50 → 100 Hz 省约 7 ms，50 → 25 Hz 多约 12 ms，大致是周期缩短或拉长量的一半（采样保持的平均等待）。
  抖动 RMS 用的是逐样本二阶差分，和采样频率有关，不能跨频率比；改用统一 25 Hz 网格上的加速度 RMS，三者为 2824 / 2603 / 2871 计数/秒²，没有明显差别。
  现场遥操作用不上 100 Hz：读主臂要 14 ms，只读主臂时循环上限约 70 Hz，再读从臂约 54 Hz。要提频得先改主臂固件里逐个舵机读、每个固定等 800 µs 的做法。
- **滤波**：照搬上一套系统的参数（单位换算成计数），滞后多了约 56 ms，抖动只降约 20%。NexArm 主臂编码器信号本身干净，这组参数下滤波不值得。
  加上预测能把滞后拉回 72 ms，但仍远不如只用预测。更轻的滤波参数没有试。
- **前瞻搜索**：用前瞻扫描数据给每个关节拟合"跟踪误差最小"的前瞻，关节 2、5 的拟合点落在测量范围（0–80 ms）之外，外推不可靠；
  实测关节 5 被过度补偿（滞后 0.4 ms），整体不比手工值好，抖动还更大。手工值保留为推荐配置。

### 2026-11-14 兼容性探测（详见 `docs/compatibility.md`）

  "主臂固件不回送舵机回复"——实测会回送，板子上的主臂固件和资料包里的源码不一致；
  "退出桥接模式会重启从臂"——实测不会，从臂进了桥接模式就一直在里面，要断电重启才能回到普通模式（桥接回调不处理 68 号指令）。
  前面记录里说"结束时从臂重启了"的地方都不成立。驱动已改为不再发退出指令。
- 主臂 6 个舵机的寄存器表已只读存档：`results/servo_memory_leader_20261114.json`。

- 让从臂退出桥接模式要两路同时断电：ESP32 由 USB 和机械臂电源共同供电，只关电源开关或只拔 USB 都不会重启（实测）。
- 判断从臂是否在桥接模式，以"是否回复 96 号读位置"为准；版本查询在刚上电的普通模式下也可能不回复，不能当判据。
